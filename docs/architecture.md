# Architecture And Contracts

## Request Flow

ADK Web -> fresh-plan reset -> trusted identity callback -> coordinator input-scope review -> structured planning -> planned AgentTool delegation -> specialist input-scope review -> authorization/audit callback -> fixed Python tool -> read-only SQLite connection -> specialist output-scope review -> plan progress update -> coordinator synthesis and output-scope review. There are no transfer sub-agents, generated SQL, external search tools, or write tools.

| Specialist | Tools |
| --- | --- |
| workforce_agent | get_headcount, get_bench_summary, list_bench_employees, list_new_hires, list_employees, get_layoff_count, get_attrition_stats |
| client_project_agent | get_client_count, list_clients, get_client_details, list_projects, get_project_details, get_project_team |
| employee_profile_agent | find_employee, get_employee_profile, get_employee_projects, get_employee_email, get_employee_manager, list_direct_reports |

Package import is side-effect-free. Importing the agent module builds model objects but does not open databases or contact Cohere. The seed entry point has no dependency on agent import or an API key. Configuration and model creation are separate from SQL and pure permission logic.

## Skills And Topic Enforcement

Four fixed runtime skill directories under `company_assistant/skills/` contain SKILL.md files with native ADK frontmatter and detailed workflows. `load_agent_skill` resolves only registered agent names and calls ADK's skill loader; malformed/missing files fail agent construction. Skill bodies become agent instructions alongside shared safety rules. They are always loaded for their assigned agent, not dynamically selected by the LLM, and do not expose scripts/filesystem tools. The shared `make_agent` factory installs all guard callbacks consistently.

`TopicGuard.before_agent` runs after trusted identity initialization. It accepts text-only input up to 8,000 characters, rejects exact configured-key values, handles simple greetings/thanks locally, and otherwise asks a tool-free model request for exactly one boolean JSON decision. The classifier gets the receiving agent's explicit scope, the current question, a bounded previous question, and the last employee ID as untrusted contextual data. A specialist's check also gets `approved_user_question`, the coordinator-approved question the delegated step belongs to, and is told to allow a supported retrieval that serves it even when the step is long or lists several items. When a specialist's check blocks a step, the user sees a distinct message ("One part of your request was blocked by a scope check…") rather than the generic out-of-scope refusal, so a blocked step is not mistaken for an out-of-scope question; the log line `Topic guard blocked: agent=<name> reason=<out_of_scope_input|out_of_scope_output>` names the layer. Independent steps for one specialist are merged into a numbered list ("Answer each of these requests: (1) …; (2) …"). It also gets `company_clients`, this company's own client names from a small cached read-only lookup (empty if the lookup fails), so a client that shares its name with a real-world business, such as Delta or Juniper, is not mistaken for an outside organization. It does not get the full session, other database rows, role authority, or tools. User permission is still decided separately even if the scope classifier allows a request.

`TopicGuard.after_model` suppresses partial text, strips commentary from function-call messages, and reviews complete text answers up to 12,000 characters. Responses containing attachments or the configured key are refused without forwarding them for review. Review requests use the same provider model but a separate fixed classification instruction, temperature zero, 64 output tokens, and a 30-second deadline per attempt; only a timeout is retried once. Errors, invalid/oversized/non-boolean decisions, and reviewer tool calls all fail closed. Scope-review calls go through the existing per-agent model-call guard; they are not counted by ADK Runner as separate agent model turns, so the callback budget is necessary in addition to RunConfig.

Each specialist has its own allowed topics, written as positive category lists in `SCOPES` (not field-by-field "only" lists). The scope guard decides topic only; which people or fields a user may see is decided by the permission callbacks, so a request for a named employee's email, manager, or direct reports is in scope and is denied or allowed by policy. A root that attempts an unrelated delegation is checked again by that specialist. Supported cross-domain questions can still be combined; a request mixing company data with an unrelated task is refused entirely. Simple greetings, relevant clarifications, permissions/service errors, and capability explanations are allowed. Rejections clear last_emp_id and the rejecting agent's prior-topic reference to avoid stale follow-ups. Scope rejections are logged as safe reason codes; the audit database remains a log of attempted tools rather than every chat message.

The guard imposes a real enforcement point around model decisions, but the semantic decision itself is probabilistic. A hostile request or database string may still fool a classifier; classification does not verify database grounding or replace authorization. SDK/debug traces may retain original model output even when it is withheld from the user-facing event stream. Keep ADK Web local and synthetic-data-only. Native skill validation and scripted callback/streaming tests are verified offline; live Cohere scope quality and latency require explicit evaluation.

## Plan-First Coordination

The root has a `RequestPlanner` callback layer; specialists retain their normal guardrails and do not recursively plan. Its first callback clears the active plan, progress, and pending-call flag and binds them to the new invocation. After identity/topic checks pass, a tool-free request to the configured model produces a JSON plan. After validation the planner folds independent steps for the same specialist into one delegation (`merge_independent_steps`), because every delegation costs several model calls; steps that depend on earlier results are never merged. Strict Pydantic models allow only registered agents, bounded nonempty tasks, up to six steps, earlier-step dependencies, and a fixed clarification code. The planner reads the first JSON object in its reply, so stray words or a Markdown fence around the plan are tolerated, but the object itself must match the strict schema exactly. A reply that arrives but is not a valid plan gets exactly one repair attempt: the rejected reply and a value-free reason (field names and error types only) are sent back, and the repair call counts against the same model-call budget. Tool calls by the planner, known-key echoes, oversized replies, provider errors, and timeouts are never repaired and stop the turn before business tools, as does a second invalid reply. Each failure is logged with its error type and the same value-free reason, never reply text.

The validated `request_plan` and progress are stored in session state. A before-model callback appends the current plan to coordinator instructions. The before-tool callback also replaces the coordinator's delegation text with the validated plan task (steps that depend on earlier results keep the model's text as added context), so names, filters, and resolved dates reach the specialist exactly as planned instead of being re-worded by the model. The planner also receives `company_clients`, so a question that only names a client, project, or person becomes a lookup instead of a clarification. Root before-tool callbacks first perform existing authorization/auditing, then enforce the next planned specialist and a single in-flight delegation. After-tool advances only that pending step, and only for the call that before-tool accepted (tracked by function-call ID), so a rejected duplicate or batched call cannot complete a step. Final text cannot be released before the plan is complete: if the model replies with text while a planned step is still outstanding, including before any delegation, the invented text is discarded and the planner issues the next planned delegation itself (bounded by the number of steps, logged without reply text). Only when the plan cannot safely continue (a delegation in flight, a stale plan, no steps left, or the bound reached) is the reply replaced by a fixed incomplete-plan message. Topic-output review still applies afterward. Capability explanations may have no steps; clarification plans have no steps and use fixed application messages. Plans are not executed as code or SQL and cannot grant authority.

`plan_next_step` is a zero-based next index (also the count of returned delegations). `plan_pending` prevents parallel or duplicate in-flight work. `plan_invocation_id` rejects stale plans. `plan_status=completed` means specialist calls returned, including errors or permission denials, not that all data retrieval succeeded. Audit records remain authorization attempts, so an authorization-allowed but plan-mismatched call need not have executed. Plan descriptions are untrusted task data; neither schema validation nor step ordering proves semantic quality or factual correctness.

The planner's system prompt is its fixed rules plus a capability table generated from each specialist's real tool list (tool names, parameter names, and the first line of each docstring) and a set of worked example plans, so what the planner believes each specialist can do cannot drift from the tools; a new tool appears in the table without editing the planner, and tests check every tool is listed and every example plan validates. The planner makes one additional model call (retries are handled by the shared model layer), a 1,536-token output cap, and an 8,000-character response cap. It uses the same callback call budget as other coordinator model requests. Previous-plan context and last employee ID can help with follow-ups; every message still requires a fresh plan. The payload also carries `current_user_id`, the verified signed-in employee ID taken from the trusted identity callback (ignored unless it is a well-formed ID), so "my email", "who do I report to", and "who reports to me" resolve to that employee without a clarification; access is still decided by the permission callbacks. It also carries the UTC `current_date` and `resolved_periods`, exact date ranges computed in Python for today, yesterday, this/last week, this/last month, this/last year, and the last 7/30/90 days; the planner copies these and does no date arithmetic, and `pending_question`: when the planner asks for clarification it stores the question, and the user's next short reply (a date, year, ID, or name) is merged with it. The coordinator topic guard receives the same pending question as its previous-question context, so a short reply is judged in context. A scope rejection clears the pending question. A named person is searched by name; the previous employee is used only for pronoun follow-ups. Greetings, rejected topics, and invalid identities stop before planning. No live plan-quality verification has been performed.

## Trust Boundaries

The process environment selects DEMO_USER_ID. A read-only database lookup supplies the actual role and reporting relationship for each attempted tool invocation. Session identity values are informational only; changing them, the ADK user ID, or a chat message cannot authorize a query.

| Capability | Employee | Manager | HR |
| --- | --- | --- | --- |
| Headcount, bench totals, clients, project metadata | Yes | Yes | Yes |
| Exit aggregates, bench names, new-hire and employee lists, project team rosters | No | Yes | Yes |
| Own profile, email, manager, project history | Yes | Yes | Yes |
| Another person's profile, email, manager, project history | No | Direct reports only | Yes |
| Direct reports of a manager | No | Own reports only | Yes |
| Find an employee by name | Self only | Self and direct reports | Everyone |

Both coordinator wrappers and specialist tools are registered in a default-deny policy. Allowing a wrapper does not authorize its child query. Unknown/inactive actors and unknown tool names fail closed. Unauthorized targets return the same permission error whether they exist or not. An authorized HR lookup can return not_found. `find_employee` has its own `search` policy: any valid actor may call it, and the tool itself returns only rows that actor may access, so an unauthorized and a non-existent name give the same empty result. Its audit record stores only the length of the searched name.

The SQL functions are internal Python APIs, not independently authenticated endpoints. The ADK callback is their enforced external invocation boundary. Anyone with local Python execution or database-file access is trusted; this development app is not a sandbox against the machine owner.

## Storage And Audit

Both generated SQLite databases default to `company_assistant/db/` inside the project, anchored to the package location rather than the process working directory. Explicit `COMPANY_DB_PATH` and `AUDIT_DB_PATH` overrides remain supported. Database files and their sidecars are Git-ignored but can still be synced by OneDrive. Existing databases must be relocated with the server stopped; startup does not silently overwrite, reseed, or migrate data.

Business tables are employees, clients, projects, and assignments. A small dataset_metadata table records the seed date. Foreign keys, status/role checks, nonnegative experience, uniqueness, and date-order checks protect generated records. Indexes support the filtering/join paths.

Runtime company connections use encoded file URIs with mode=ro and query_only enabled. Each connection is explicitly closed. The separate seed CLI is the only intentional company-data writer, and reset must be explicit.

The seed CLI also supports `--append-count N`: it adds exactly N dummy employee rows and N explicitly marked dummy audit rows, preserving existing records and leaving clients/projects/assignments untouched. It reuses the base seed's status/date distribution and existing managers, allocates new four-digit IDs, and never grants new HR/manager privileges. Only this offline seed operation attaches the audit database to its writable company connection for a combined transaction; runtime query and audit connections remain separate. Failed inserts or foreign-key checks roll back both sets of new records. Dummy audit reasons start with `dummy_` and correlation IDs with `dummy-seed:`; these are synthetic test events, not claims that actual tools ran.

Audit writes use a distinct database and connection with a five-second busy timeout. Each callback records UTC timestamp, trusted actor, tool name, normalized allowlisted arguments, allow/deny reason, and correlation ID before tool execution. These are authorization attempts, not query-success records. Raw wrapper requests, credentials, complete prompts, and result bodies are excluded. Failure to persist audit blocks execution and emits a sanitized error to stderr. Audit records are not exposed as agent tools.

An invalid/missing database can prevent even identity resolution and durable auditing; the tool still fails closed. No record is claimed when audit storage fails. ADK's developer traces can contain the synthetic conversation/tool data and must not be shared as if sanitized audit logs.

## Data Semantics

- Headcount: active plus bench. Bench: explicit status, not absence of assignments.
- Layoffs/attrition: exit_date in the selected calendar year, January 1 inclusive to next January 1 exclusive. Attrition includes resigned, laid_off, terminated, and retired. No attrition rate or historical headcount is inferred. The coordinator establishes one UTC request date, shared through async context with nested tools, so defaults remain stable across midnight.
- Clients: total includes active/inactive, with breakdown. Project filters default to all statuses.
- Team size: distinct currently employed assignees with a started assignment and no end date or an inclusive end date at/after the query date. `get_project_details` returns the count only; `get_project_team` (manager/HR) lists those same current assignees.
- `list_employees` can add each listed person's current project names (`include_projects`) in one query, so a list "with project names" never needs one lookup per person. It shows current assignments only; past project history stays behind the per-employee authorization. `list_employees` lists current employees (active or bench) unless a status, an exit window, or `include_departed` is given. Employee lists (`list_employees`, `list_new_hires`, `list_bench_employees`, `list_direct_reports`) return 20 rows by default (a `limit` of up to 100 when the user asks for more) with the total and a `truncated` flag. They never include exit reasons, manager links, or internal roles. "Unassigned" means an active employee with no current assignment, which is different from the explicit bench status. `project_name` and `client_name` limit a list to people currently on that project or on any project of that client (an unknown name is `not_found`, not an empty list), and `order_by` (name, join_date, exit_date, with `descending`) answers "longest serving", "newest joiners" and "most recently left". Every agent is also told to apply each constraint the user states and to say so when one cannot be applied, and the footer lists the filters that were applied so a missing one is visible. `assigned` is the opposite filter (only people who currently have a project) and `assigned=false` equals `unassigned`; both are built from one shared condition, and combining `assigned` with `unassigned` is rejected. A date window always needs both bounds; a single bound is rejected.
- Employee project count: distinct project IDs. History groups repeat assignment periods under one project.
- Approximate experience: elapsed days / 365.2425 plus prior experience; display rounds to two decimals. Departed staff stop accruing company tenure at exit. One employment period per person is modeled.
- Names: trimmed, case-insensitive exact match; unique client/project names. Employee IDs: normalized E plus four digits. Lists are sorted; long lists are capped as described above.

Each result has status and data, plus a UTC computation date and effective filters where relevant. Errors have status, code, and safe message. Codes: invalid_argument, not_found, permission_denied, clarification_required, service_unavailable; the planner adds plan_required and plan_mismatch. Valid empty lists are successes. Profile results contain no incidental email, exit reason, internal role, or manager relationship. Email, manager, and direct reports are returned only by their own tools (`get_employee_email`, `get_employee_manager`, `list_direct_reports`), each authorized with the same rule as profiles. Exit reasons and internal roles are never returned by any tool.

## Conversation State

Successful authorized employee lookups set last_emp_id through ToolContext.state. Missing/denied/invalid lookups clear stale references. Every follow-up is authorized again. Multi-employee turns clear the pronoun reference; session-local per-target markers are forwarded through AgentTool and cleared at turn boundaries. These markers are not authorization inputs.

The pinned AgentTool creates nested sessions and propagates ordinary state deltas; temporary marker visibility was insufficient for parent-level multi-target tracking in runtime tests. The implementation therefore does not depend on temporary child markers for that decision. Sessions remain isolated and in memory with the documented command. A restart is required when switching demo identities.

The root combines permitted portions of multi-domain requests and preserves denials. Manager access to all bench names does not imply access to all corresponding project histories. Database strings are untrusted data; prompt rules are defense in depth, not the access-control mechanism.

## Runtime And Testing

Cohere uses cohere_chat/command-a-03-2025 through LiteLLM, wrapped by `ResilientLiteLlm` (`company_assistant/model_resilience.py`), which every model use shares: scope guards, planner, coordinator, and specialists. It retries transient provider errors (HTTP 429, 408, 5xx, connection errors, timeouts) up to three times with backoff that honors Retry-After, never retries after output has started streaming, and optionally paces calls to `MODEL_CALLS_PER_MINUTE` so a rate-limited key is spent rather than exceeded. LiteLLM's own retry is disabled so retries are not multiplied, and the guard and planner make a single attempt each. A rate limit that outlasts the retries is reported as a rate limit, not as a failed safety check. A monthly provider cap (the Trial key's 1,000 calls a month) is recognized from the provider message, is never retried, and is reported with its own message, because waiting cannot clear it. Requests have a 30-second provider timeout, specialists a 120-second timeout, root a 300-second timeout (a paced, multi-step question needs well over a minute), and the launch command limits model calls per run to 12. Callback counters provide an additional per-agent bound; nested runs should not be interpreted as one global call counter.

Direct dependencies are pinned in requirements files. Full transitive resolution is checked with pip check and pip-audit in CI. The known filelock constraint conflict is an unresolved release gate, not an accepted security waiver. See the README for details.

Unit tests cover pure policy/validation and mocked failures. Integration tests use isolated files and real ADK runners with scripted models. Network access is blocked except loopback needed by Windows asyncio. The opt-in paid smoke test is separate from the offline suite. Semantic model behavior and prompt-injection resilience still require the live evaluation checklist.

Out of scope: shared/production deployment, real HR data, SSO, custom frontend, salaries, editing, RAG, cross-session memory, rehire histories, charts, and exports.
